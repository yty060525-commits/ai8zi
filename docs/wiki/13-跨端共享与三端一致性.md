# 13 跨端共享与三端一致性

「三端」指同一份逻辑的三份实现：浏览器（TypeScript）、Linux 服务器（Node `.mjs`）、Windows 桌面（Rust）。本页面讲**哪些是真共享（只有一份代码）**、**哪些是有意复刻（必须逐字节对齐）**，以及靠什么判据把守。

## 真共享：中文闸门

[client/src/shared/chineseGate.ts](../../client/src/shared/chineseGate.ts) 是全项目唯一实现，导出：

| 导出 | 作用 |
| --- | --- |
| `FIELD_NAME_ZH` | 字段名中文对照表，模型输出里出现英文字段名时用它替换 |
| `isChineseOnly` / `nonChineseKinds` | 判定与分类（哪类脏字符） |
| `enforceChinese` | 硬约束 |
| `sanitizeChatText` / `sanitizeAnalysisText` | 含拉丁字母/数字/特殊符号的整段抹掉 |

消费方：

- 服务器直接 import TypeScript 源文件（Node ≥ 22.5 原生加载）：[server/ai.mjs](../../server/ai.mjs) 第 3 行、[server/chat.mjs](../../server/chat.mjs) 第 21 行与第 335 行转出。
- 浏览器经 [elements.ts](../../client/src/features/chart/elements.ts) 第 53 行的转出（`sanitizeChatText` / `sanitizeAnalysisText` 等），全站从那里取用，不再各自实现。
- 单测把守「只有一份」：[gate-single-source.test.ts](../../client/src/__tests__/gate-single-source.test.ts)。
- **服务端洗过即终判**（#136）：[server/chat.mjs](../../server/chat.mjs) 拿到模型正文后先 `sanitizeChatText`，洗净为空就换 provider、全失败返回 `failed`。因此客户端 [chatEngine.ts](../../client/src/data/chatEngine.ts) 收到 `completed` 却洗成空时**不再静默改用浏览器里那份本机密钥重答**，而是就地报错 —— 否则连着服务器却由另一把密钥作答，用户看不出回答出自哪条通道。落本机只保留「服务器不可达」与「服务器报错且本机配了凭据」两种明确情形。

## 缓存键：口径变更的记账本

三份实现，形状相同、版本号**分两条账**：

- 服务器：[ai.mjs](../../server/ai.mjs) `cacheKey`，当前 `['v15', model, gender, 四柱, task.type, year, month, birthYear, toneBucket]`，按 5 度一档分桶。注释里 v9→v15 每一版为什么作废重算都写清了。
- 桌面：[lib.rs](../../client/src-tauri/src/lib.rs) `cache_key`，当前 `v11|…`。**任务键的 v15 / v11 不是同一个数** —— 两边各查各的库(v15 在服务器 sqlite、v11 在桌面 sqlite)，键串永不互比，所以版本号只要求「本端提示词字节变了就升」，不要求跨端同数。这一点曾被我读成缺陷，实测确认两端各自注释里的升版原因逐条对得上后才排除。

**natal 键序是前缀的一部分**(#132)：三端都把 natal 整段 JSON 放在任务指令之前，`JSON.stringify` / `serde_json::to_string` 都按插入顺序出字节，所以「同序」不是风格问题而是缓存命中问题。桌面曾写成 `solarDate→zodiac→dayMaster` 与 `hiddenStems→tenGods`(另两端是 `dayMaster→zodiac→solarDate`、`tenGods→hiddenStems`)，而 lib.rs 的注释恰恰写着「与另两端 natal 同序」—— 这句话当时没有任何校验器(prompt-parity 只比四个提示词常量，server 侧 parity 只在两份 JS 之间比)。判据见 [natal-key-order-cross-end.test.ts](../../client/src/__tests__/natal-key-order-cross-end.test.ts)：读三份源码字面量的顶层键序、投影到 `NATAL_SHARED_KEYS` 后逐位比对。
- 聊天：[chat.mjs](../../server/chat.mjs) `chatCacheKey` 与桌面 `chat_cache_key` **必须同名同版本**(当前都在 `chatv6`)。理由是聊天证据由客户端 [chatEngine.ts](../../client/src/data/chatEngine.ts) 构建、三通道共用同一份字节，服务端措辞一变，桌面旧答案同样是旧口径 —— 一边升一边不升，就是「换个设备答案口径不一样」。#131 实测踩过：服务端已到 chatv6，桌面停在 chatv5，而它上一行注释写着「与服务端同名键对齐」。判据见 [cache-key-cross-end.test.ts](../../client/src/__tests__/cache-key-cross-end.test.ts)。

**规则**：改提示词正文、改 natal 键顺序、改输出要求 —— 任务键三处各自升版，聊天键两端同步升；否则旧缓存继续命中，改动像没生效。

## Qwen 显式缓存：靠分段顺序不靠打标

走 Qwen 时只有够最小可缓存前缀（约 1024 token）才打 `cache_control: {type:'ephemeral'}`；实现见 `withQwenCacheMark`（[ai.mjs](../../server/ai.mjs)）与 `qwenCacheableContent`（[deepseekAdapter.ts](../../client/src/data/deepseekAdapter.ts)）。命中率是实测出来的，不是推断：跨任务恒定的内容（本命事实数据）排在会分叉的任务指令之前，四类任务的全局公共前缀约 1714 字。测量脚本 [qwen-prefix-measure.test.ts](../../client/src/__tests__/qwen-prefix-measure.test.ts) 直接调真实拼装函数取样，把任何可变段挪回前面它会指出断在哪一对请求。

## 一致性判据

- [prompt-parity.test.ts](../../client/src/__tests__/prompt-parity.test.ts)：比对四个指令常量的定义文本（含 Rust 那份）。
- [server/test/prompt-parity.test.mjs](../../server/test/prompt-parity.test.mjs)：更进一步，调两端**真正的拼装函数**逐字节比「natal 标题与共有键顺序 / 任务指令 / 输出硬性要求 / 语气标题」。常量抄对但拼装顺序各写一份，只有这一份查得到。
- [qwen-cache-mark.test.ts](../../client/src/__tests__/qwen-cache-mark.test.ts)、[channel-routing.test.ts](../../client/src/__tests__/channel-routing.test.ts)、[ai-settings.test.ts](../../client/src/__tests__/ai-settings.test.ts)、[admin-owner-label.test.ts](../../client/src/__tests__/admin-owner-label.test.ts)。
- [cache-key-cross-end.test.ts](../../client/src/__tests__/cache-key-cross-end.test.ts)：读两端源码字节钉聊天键 —— 版本段两端同值、声称「与服务端对齐」的注释不许比代码旧、字面量逐格形状(第 2..7 段六个 `{}`、第 8 段固定 `chat`、第 9 段 `{:016x}`，合计 11 段与服务端同构)、哈希宽度各自稳定。#131。
- [natal-key-order-cross-end.test.ts](../../client/src/__tests__/natal-key-order-cross-end.test.ts)：三份源码 natal 顶层键序投影比对 + 「调候紧随旺衰、先于起运」三端各自成立。#132。
- [provider-spec-cross-end.test.ts](../../client/src/__tests__/provider-spec-cross-end.test.ts)：通道端点/模型名三端逐字一致，温度三端同源。**#133** 实测踩过：`deepseekAdapter.ts:141` 注释写「参数与服务器端、桌面端保持一致」，但 Qwen 的 temperature 浏览器直连与服务端都是 `0.3`(服务端注释「已关闭思考的 Qwen 用低温度更稳定」)，桌面 `provider_temperature` 却停在 `Some(1)` —— 同一命盘同一个问题在网页和桌面得到不同温度的答案。修复时把 Rust 签名从 `Option<i32>` 改成 `Option<f64>`(i32 表达不了 0.3，会把小数静默截回整数、重新分叉)。判据读三处各自的来源(CHANNELS 行内字段 / ai.mjs 的 `body.temperature = X` 行 / lib.rs match 表)，归一化数值后逐格比，并钉死「Qwen==0.3」防 null==null 蒙过。⚠ CHANNELS/PROVIDERS 里的 `label:` 是展示名(允许各端不同)，不在比对范围；进正文的中文通道名由 PROVIDER_LABEL/label() 那条单独钉。
- [credential-blank-caliber-cross-end.test.ts](../../client/src/__tests__/credential-blank-caliber-cross-end.test.ts)：保存凭据时对空白的处理三端同源。**#134** 实测踩过：`aiSettings.ts:29` 与 `ai-settings-browser-creds.test.ts` 第 69–70 行的注释都声称「桌面 save_ai_credential 见空密钥直接报『密钥不能为空』」，但这句话从没被任何校验器读过 —— 桌面原写 `if secret.is_empty()`(trim **前**)，纯空白 `"   "` 在 `.is_empty()` 下为 false ⇒ 桌面把空白串当有效密钥落进 keyring、界面报「已配置」，而这份串发上游必失败(正是那句注释要防的事)。服务端 `saveProviderKey` 用 `key.trim()`、浏览器 `saveAiCredential` 先 trim 再判空，只有桌面对不上。修复：Rust 改 `let trimmed = secret.trim(); if trimmed.is_empty()` 并存 `trimmed`。判据的关键不是「有没有 trim」而是「判空用的是不是 trim 后的值」—— 用 `not.toMatch(/if\s+secret\.is_empty\(\)/)` + `toMatch(/trimmed\.is_empty\(\)/)` + `set_password(trimmed)` 三面钉死。
- [tone-text-cross-end.test.ts](../../client/src/__tests__/tone-text-cross-end.test.ts)：语气指令五档正文三端逐字节相同。**#135** 实测踩过：`server/test/prompt-parity.test.mjs:12` 自陈「语气段的措辞文本也各端一份，只比标题」—— 标题钉了、正文从没比过。浏览器直连 `toneInstructionText` 用的是缩写版(`语气：中立客观——好坏如实平衡说明。`)，服务端/桌面是完整版(`语气：中立客观。好坏都如实、平衡地说明…`)，同一滑杆值在网页直连拿到的措辞指令与另两端不同。修复：把 adapter 五档统一成与服务端/lib.rs 逐字节一致的完整版。判据按档位阈值一致、每档唯一，取三端五条正文排序后 join 比对，并留一条反向钉子(不许再有「档名——」缩写句式)防回归。⚠ 语气段排在 OUTPUT_RULES_TEXT 之后、不在 Qwen 公共前缀里，所以这次统一不影响缓存命中，纯粹是「同一问在不同通道拿到同一条指令」的口径问题。

## 存量数据不会自动变干净

改了提示词只影响新生成的批断。已落库的正文（`aiTasks.*.analysis.explanation`）和旧姓名仍带脏串，而详情页、复制、导出都是**直读存量文本**。所以：

1. 写入时清洗一次（`sanitizeAnalysis`）。
2. 展示与复制读取时再兜一道（`sanitizeAnalysisText`、`readableName`）。
3. 遇到「又出现英文了」先分清新生成还是旧存量：查线上产物里该标识符出现次数，再比对截图时间与修复提交时间。
