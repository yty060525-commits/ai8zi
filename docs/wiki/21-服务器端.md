## 数据库

[db.mjs](../../server/db.mjs) 第 12–48 行建表：

- `users(id, username, pass_hash, salt, role, created_at)`
- `sessions(token_hash, user_id, expires_at)` + `idx_sessions_expires`
- `records(...)` + `idx_records_user`、`idx_records_user_time(user_id, updated_at DESC, created_at DESC)`（免临时排序）、`idx_records_name`、`idx_records_pillars`
- `settings(key, value)` —— 存 `ai.provider`、`ai.key.<id>`
- `ai_cache(cache_key PRIMARY KEY, chart_sig, payload, created_at)` + `idx_cache_chart_sig`

`chart_sig` 是从缓存键派生的列，老库打开时自动补列回填（同文件第 55–67 行）。有了它，删盘/清缓存不再用前导通配 LIKE 全表扫描，而是索引精确删除，任务缓存与聊天缓存一并清掉。

**注意**：`server/data/*.sqlite3` 是真实用户数据，任何测试和脚本都不得写入或删除。

## 中止传播：客户端点「停止」后服务器不再花钱（#139 / #140）

`POST chat` 与 `POST records/:id/ai/task` 是唯二会连着打三条上游通道的路由，所以它们是唯二需要把「客户端已经走了」这件事接进来的地方。链路是三跳，每一跳都有判据：

1. [app.mjs](../../server/app.mjs) 的这两条路由各给 `res` 挂 `close` 探针，**只认 `writableEnded === false` 的那次 close**，用它 abort 一个 `AbortController`；
2. [chat.mjs](../../server/chat.mjs) 的 `runChat(db, user, body, opts)` 与 [ai.mjs](../../server/ai.mjs) 的 `runOneTask(db, record, task, tone, preferred, opts)` 用同一句 `abandoned()` 做两件事 —— 放弃后不再试下一条通道、且**不把这份没人读过的结果写进 `ai_cache`**；
3. [ai.mjs](../../server/ai.mjs) 的 `callProvider(..., callerSignal)` 把调用方的信号桥接进自己那个 150s 超时控制器。

⚠ 第 2 条里的「不写缓存」才是这条修复的重点，省下的钱只是副产品：首轮问答按 `(record, question, model, tone)` 落缓存，用户点停止往往正因为模型在跑偏 —— 让那份跑偏答案占住这个键，下次重问同一句直接命中缓存、原样返回同一个坏结果。批断这一侧的量级更大：一次批断是十几个任务 × 三条通道，而每个任务的产物同样按 `(record, task, model, tone)` 占住缓存键。

⚠ 「答案已经写出、正文还没被读完」这一刻的断连**测不到，也不该由缓存兜**（Node 24 两份探针实测：`res.end(大正文)` 之后客户端取消响应体或读一格就毁连接，`close` 里 `writableEnded` 已经是 `true`，与正常读完一模一样；而写缓存发生在 `json()` 之前）。这一路按「已完成」处理，判据钉的是这个方向，别反过来要求它不进缓存。

判据分两份文件：[chat-abort.test.mjs](../../server/test/chat-abort.test.mjs)（6 条）与 [task-abort.test.mjs](../../server/test/task-abort.test.mjs)（4 条），都跑 `node --test test/<文件>`。三个设计约束：① 真实 `callProvider` / `runTaskForProvider` 内部自己 new 控制器，从外部只能间接观察，所以 `createApp` 额外导出 `setProviderCaller`、`setTaskCaller` 测试接缝，`runChat` 认 `opts.callProvider`、`runOneTask` 认 `opts.runTask`；② 它们是 `.mjs`，进不了客户端那张 `CRITERIA` 表（表会把 `file` 拼进 `client/src/__tests__/`），改由 [delivered-files-in-tree.test.ts](../../client/src/__tests__/delivered-files-in-tree.test.ts) 单独一句钉它们在 HEAD 树上；③ 「循环开头那道 `abandoned()` 闸门」用挂到断连才交结果的替身**测不到**（第一轮就 return 了，压根不走第二轮），批断那边另配一条「第一个通道立刻失败、但等到断连才交失败」的用例把第二轮逼出来。客户端那一半的前提（`signal` 真透传到 `serverFetch`）钉在 [chat-engine.test.ts](../../client/src/__tests__/chat-engine.test.ts) 的「中止信号要一路带到服务器请求上」。

变异验证读数（每条独立跑）：聊天侧 —— 去掉 `opts.signal` 转发 → 2 红；`abandoned()` 恒为假 → 1 红；删掉换通道前的 `abandoned()` 闸门 → 1 红；保留迟到写缓存 → 1 红；摘掉 `res.on('close')` → 1 红；摘掉 `finally` 里的 `removeListener` → 1 红；监听 `finish` 而非 `close` → 1 红；客户端删掉 `signal` 透传 → 1 红。**仍存活的一条**：把探针改成无条件 abort（删掉 `!res.writableEnded`）全绿 —— Node 在 `res.end()` 后本就自动摘除 `close` 监听器，这个条件在本端不可观测，属防御性写法，不是漏测。批断侧 —— 去掉 `opts.signal` 转发 → 2 红；保留迟到写缓存 → 1 红；探针挂到 `req` 上 → 1 红；删掉循环开头的 `abandoned()` 闸门 → 1 红（只有上面第 ③ 条那种「等到断连再交失败」的替身杀得掉，早期夹具全绿即存活）。

## 判据空白 #141：客户端中止闸门本身没人读过

上面那条链路的最后一环（浏览器这一侧「服务器请求被中止 ⇒ 就地收口」）此前**一次都没被断言碰过**。[chat-engine.test.ts](../../client/src/__tests__/chat-engine.test.ts) 里守的是 `signal` 有没有透传出去，而 `askChat` 的 catch 里那句 `error instanceof DOMException && name === 'AbortError'` 是另一回事：把它删掉，代码不报错、其余用例照旧全绿，实测行为变成「用户点了停止 ⇒ 又用浏览器里那份本机密钥打了一次上游」，与 #138/#139 想省的正是同一笔钱。兄弟路径早有覆盖（批断侧 `deepseekAdapter.abortResult`、云端脏串不再落本机），只有聊天中止这一格是空的。

现在由「点「停止」后不得再用浏览器里那份本机密钥重答(#141)」钉住：夹具必须给本机凭据（否则落本机那条路压根启动不了，判据空转），断言三件 —— 回执仍是「已取消」、`chatDirect` 没被调用、服务器请求只发一次。另配一句**反向钉子记录现状**：`askChatLocal` 在中止时仍会进入一次（它第一步 `listBaziRecords` 必然执行，只是没东西可打），实测读数 1；若有人把落本机的入口整个拆掉，这句会红，那时先确认是不是有意的口径变化。

变异读数（每条独立跑，均只红这一条）：整句删掉中止闸门 → 红；改成只判断不返回（当成 offline 处理）→ 红；把 `AbortError` 换成 `TimeoutError` → 红。三条都杀得掉，说明这句闸门现在有了真正的守门人。
