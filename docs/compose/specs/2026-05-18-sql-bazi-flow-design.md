# SQL 与八字排盘流程改造规格

## [S1] 目标与范围

将现有前端 mock 排盘流程改为本地可持久化的排盘流程：公历、农历、八字三种输入均能生成基础命理数据；基础数据由程序确定性计算；格局、身强身弱、喜忌及其解释由 DeepSeek API 补充；所有输入和结果保存到 SQLite；提交后自动跳转到底部第二分类“记录”页。

本次不实现服务器同步、年度/月度批量 AI 运势生成、称骨完整规则库或账户计费模块。未配置 API 时，基础数据仍必须保存，AI 字段显示未连接或失败原因。

## [S2] 输入与确定性计算

公历和农历表单保持一致的日期、时间、出生地区输入体验。农历额外保留闰月开关，但不再使用与公历不一致的零散时间选择方式。

八字表单接收四柱干支。程序校验干支格式与阴阳配对后，通过 `Solar.fromBaZi` 反推出生年份候选；用户选择候选年份后，再复用公历/农历计算路径，生成四柱、农历/公历对应日期、生肖、五行、五行比例（已有库数据可计算部分）、藏干、十神、纳音、日主、起运和大运等常规基础信息。程序不能把这些事实交给 AI，也不能擅自选择候选年份。

## [S3] AI 分析边界

AI 请求只接收已经计算好的基础数据，要求返回结构化的格局、身强身弱、喜用/忌用五行及解释字段。默认使用 DeepSeek OpenAI 兼容接口和 `deepseek-chat`，地址、模型和密钥从本机配置读取，密钥不得出现在源码、规格、测试 fixture 或提交内容中。

API 超时、未配置或返回格式错误不能阻止基础数据入库；记录中标注 AI 状态和错误信息，允许后续重试。

## [S4] SQLite 持久化与适配

Tauri Rust 层负责 SQLite 初始化、迁移、插入和查询，至少保存人物主记录、原始出生输入、确定性计算结果、AI 分析结果、计算时间和 AI 状态。前端通过类型化 Tauri command 适配器调用，不在 React 组件中拼接 SQL。

浏览器/Vitest 环境继续使用内存 adapter，仅用于测试；生产 Tauri 环境默认使用 SQLite adapter。记录页从 adapter 读取真实已保存记录，应用重启后仍可读取。

## [S5] 页面流程与展示

提交成功后关闭弹窗、清除排盘页结果展开区并切换到“记录”页。记录列表直接展示新保存的人物及基础八字摘要；点击后进入详情，基础信息区域展示确定性结果，AI 区域展示格局、身强身弱和喜忌状态/内容。

删除加载动画及 queued/running 的长时间模拟流程。提交过程只保留必要的禁用/错误反馈，不渲染加载动画。基础计算失败时留在输入弹窗显示错误，不创建半成品记录。

## [S6] 验收与测试

- 三种模式都能提交；八字模式先选择候选年份，不再因“暂不生成”失败或静默选择年份。
- 农历和公历的时间输入语义一致，闰月仍可表达。
- 程序计算结果包含基础四柱及已有常规字段，且不依赖 AI 返回。
- 提交后自动进入记录页，新记录可见；刷新/重启后的正式 Tauri 环境从 SQLite 读取。
- API 未配置、失败或格式错误时，基础记录仍存在并显示明确 AI 状态。
- 不出现加载动画、不在排盘页展开基础结果。
- Vitest 覆盖八字计算、保存与导航；Rust/SQLite 层覆盖建表、插入和查询；`npm test -- --run`、`npm run build` 和 Tauri 检查均通过。
